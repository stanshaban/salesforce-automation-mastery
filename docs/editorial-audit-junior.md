# Junior course editorial and technical audit

Checked: 2026-11-09. Scope: 28 English lessons, J01–J28, plus `data/course-meta-junior.json`.

All lessons contain an explanation, a Northstar example, a concrete activity with expected results, an exercise with acceptance criteria, questions with answers, a recap, primary sources, and a distinct illustration brief. Visible instructional text is approximately 694–928 words per lesson, excluding code and illustration prompts. Callouts use the shared `idea`, `action`, `check`, and `warning` vocabulary; the interface supplies their icons and quotation styling.

## Changes by module

- **J01–J06 — foundations:** CRM, customer, salesperson, manager, application, org, record, and acceptance criteria are introduced explicitly. Anna and Max are salespeople, Oleg manages the team, and Irina is the customer. Early exercises work on paper. Browser-based Playground entry precedes developer tooling. Product availability is not assumed.
- **J07–J10 — data and application:** standard-object choices precede custom development. Opportunity creation is not presented as requiring Lead conversion. Person Accounts are identified as a separate design choice. Actual starter names and picklist values are used. Duration and calculated end are declared additions, not falsely described as existing starter fields. Historical appointments remain editable under the targeted time validation. Master-Detail experiments are isolated; the core Test Drive remains an independently owned Lookup design. Presentation is distinguished from security.
- **J11–J16 — access:** permissions are expressed as user/operation/record/field checks. Additive grants, broad existing assignments, related-record access, and negative tests are included. No Branch field or branch-isolation guarantee is invented. Manual-share retention is tied to the current org setting. Restricted-user evidence is required; license-limited or unperformed tests remain explicitly unperformed. Max's service-review role is a declared exercise persona rather than an unexplained change to the story.
- **J17–J22 — automation and Apex:** the reminder Flow explicitly requires enabling activities on Test Drive, which the core starter disables. A Task is not described as an email. Create-only qualification and a Custom Error fault route define duplicate and failure behaviour. Apex syntax, null handling, and collections are taught before queries. The pure slot example is labelled a simulation. Database operations use explicit user mode. The trigger processes every pending record and performs no redundant self-DML. Transaction rollback is verified by requerying. Tests assert behaviour and include a deliberate-defect exercise; coverage alone is not treated as correctness.
- **J23–J28 — interface and handover:** HTML elements, JavaScript arrays/objects/classes/getters, template binding, and events are introduced before LWC composition. The four-state preview uses declared sample data. The real record form requires a real accessible record and record-page context. Parent-child communication uses a small primitive event payload and read-only incoming data. Debugging distinguishes browser contracts, validation, permissions, and Flow prerequisites. Handover separates metadata from business records and uses the learner's own repository or portal upload. The capstone has an honest small scope and an identifiable reviewed version.

## Technical caveats and source checks

- The starter and authored component examples target **API 68.0**. Current official access-mode documentation differs from older PDF guidance about defaults. Lessons use `WITH USER_MODE` and `as user` explicitly and avoid a timeless claim about default execution. See [database access modes](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-classes-enforce-usermode.html) and the [trigger release note](https://help.salesforce.com/s/articleView?id=release-notes.rn_apex_triggers_system_mode.htm&language=en_US&release=262&type=5).
- J14 checks **Keep manual shares when transferring records** before predicting transfer behaviour. It distinguishes a surviving manual share from access acquired through new ownership. See [the current setting](https://help.salesforce.com/s/articleView?id=platform.security_sharing_keep_manual_transfer.htm&language=en_US&type=5).
- J21 presents a relevant subset of the save sequence and links to the versioned [official order of execution](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-triggers-order-of-execution.html). It does not present a classroom timeline as the complete platform sequence.
- The examples were inspected against the supplied metadata and primary documentation. JSON schemas, IDs, English-only text, illustration uniqueness, XML snippets, and ordinary JavaScript syntax were checked locally. **Salesforce deployments, Apex compilation, Apex tests, Flow execution, and restricted-user checks have not been run in an org during authoring.** Learners must execute and record those checks; the lesson text does not provide fabricated results.
- Relationship deletion and temporary validation-failure experiments are restricted to disposable learning records and configuration. The fixed-size Junior bulk exercise does not claim large-data-volume readiness or a complete scheduling-conflict solution.

No existing root curriculum, portal logic, starter metadata, or other tracks were overwritten by this authoring pass. Images are supplied separately from the unique briefs in each lesson.
