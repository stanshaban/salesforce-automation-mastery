# Prepare a Salesforce Portfolio for Review

JR07 · jobs · About 60 minutes with practice

![A small project display with an application, a simple architecture diagram and test evidence](https://sam-portal-production.up.railway.app/lesson-images/JR07.jpg)

Make one project easy for another developer to understand, run and assess.

## Before you begin

- A completed Salesforce exercise or project.
- Basic Git and repository skills from the Junior path.

## What you will learn

- Explain the project before the folders.
- Make setup and verification repeatable.
- Demonstrate a decision and its limits.

## 1. A portfolio is a reviewable explanation

A repository full of metadata is not yet an effective portfolio. A reviewer needs to know what the project does, which part you built, how to try it and what its limitations are. Start with one project you understand well. The Northstar test-drive application is suitable because it connects a visible user workflow to data, automation and tests.

Label it as a training project and describe its fictional business context. Explain who uses the feature: a salesperson records a customer’s test-drive request. The customer is represented by a Contact record and does not automatically have a Salesforce login. This small detail demonstrates that you understand the user and data model rather than only the code.

> **💡 Key idea**
>
> Make the reviewer’s first five minutes useful: purpose, demonstration, setup and evidence.

## 2. Write a README that answers practical questions

Begin with a short problem statement and a screenshot or brief recorded demonstration. Then explain the main objects and the flow of one successful request. Add prerequisites, installation commands that you have actually checked, the test command and the expected result. If a feature requires an Agentforce-enabled org or a separate product, say so before the setup steps.

Include a short design decision section. For example, explain why Test_Drive__c uses lookups and how that affects its access model. A decision is stronger when it includes a trade-off, not just a claim of best practice. Add known limitations such as mock availability or the absence of a real calendar integration. These help a reviewer distinguish the implemented scope from future ideas.



**Reusable working prompt or template**

```text
# Northstar Test-Drive Training Project

## Problem and users
## Short demonstration
## What I implemented
## Data model and request flow
## Prerequisites and setup
## Tests and observed results
## Design decisions
## Known limitations
## Next improvements
```

## 3. Keep the repository safe and reproducible

Before making a project public, inspect the files you are about to publish. Exclude authentication state, private keys, local configuration containing secrets and real customer data. Use synthetic records for demonstrations. The SAM starter already excludes common Salesforce authentication directories, but an ignore file cannot remove a secret that was previously committed.

Use a separate development org and the repository instructions to rehearse setup. If you cannot test a step, label it unverified and explain the dependency. A screenshot of a successful interface is useful, but it does not prove that a clean checkout can reproduce the project. Capture the actual test output and the commit it belongs to, without including credentials.

> **⚠️ Watch out**
>
> A public portfolio should contain work you are authorised to share and synthetic data. Do not copy private employer code into it.

## 4. Guide the reviewer through one important decision

Prepare a two-minute walkthrough: the user problem, the visible feature, one key implementation decision and the verification. Open the relevant code instead of browsing through every folder. Show a failure case as well as a successful request. For example, an unavailable vehicle should produce a useful error rather than a misleading success message.

Ask a peer to follow the README from a clean starting point. Record where they hesitate and improve those instructions. The aim is not to remove every question; good projects invite technical discussion. The aim is to make that discussion about your decisions and evidence rather than missing setup details.

> **🔎 Check your understanding**
>
> A reviewer can identify the project’s context, reproduce a supported path and find the tests without asking you where to start.

## ⚡ Independent practice: Apply this to your own search

Prepare one portfolio repository and rehearse a short review walkthrough.

1. Write the README using the structure above.
2. Add a small diagram and a synthetic-data demonstration.
3. Review publishable files and repository history for private material.
4. Rehearse setup in a suitable development environment.
5. Ask a peer to review the README and record one improvement.

### Your work is ready when

- Training context, ownership and limitations are explicit.
- Setup and test instructions match the project.
- The demonstration includes a success and a failure case.

## 🔎 Check your understanding

Answer in your own words before reading the explanations.

### 1. Does a screenshot prove reproducibility?

**Answer:** No. It shows one observed state. Setup instructions and repeatable tests provide different evidence.

### 2. What makes a design decision useful to a reviewer?

**Answer:** The requirement, chosen approach, alternative and trade-off are clear.

### 3. Why is one well-explained project often enough to begin?

**Answer:** It gives concrete material for a technical conversation; adding unexplained repositories does not automatically add evidence.

## What to take away

- Explain the project before the folders.
- Make setup and verification repeatable.
- Demonstrate a decision and its limits.
