## 02 · A portfolio is a reviewable explanation

> 🎬 ЭКРАН. Раздел «A portfolio is a reviewable explanation». Продолжай показ подготовленного примера. Выдели входные данные и решение именно этого раздела. Не прокручивай целый урок вместо демонстрации. Если это аналитическое упражнение, заполняй его рабочую таблицу по одному решению.

A repository full of metadata is not yet an effective portfolio. A reviewer needs to know what the project does, which part you built, how to try it and what its limitations are. Start with one project you understand well. The Northstar test-drive application is suitable because it connects a visible user workflow to data, automation and tests. Label it as a training project and describe its fictional business context. Explain who uses the feature: a salesperson records a customer’s test-drive request. The customer is represented by a Contact record and does not automatically have a Salesforce login. This small detail demonstrates that you understand the user and data model rather than only the code.

## 03 · Write a README that answers practical questions

> 🎬 ЭКРАН. Раздел «Write a README that answers practical questions». Продолжай показ подготовленного примера. Выдели входные данные и решение именно этого раздела. Не прокручивай целый урок вместо демонстрации. Если это аналитическое упражнение, заполняй его рабочую таблицу по одному решению.

Begin with a short problem statement and a screenshot or brief recorded demonstration. Then explain the main objects and the flow of one successful request. Add prerequisites, installation commands that you have actually checked, the test command and the expected result. If a feature requires an Agentforce-enabled org or a separate product, say so before the setup steps. Include a short design decision section. For example, explain why Test_Drive__c uses lookups and how that affects its access model. A decision is stronger when it includes a trade-off, not just a claim of best practice. Add known limitations such as mock availability or the absence of a real calendar integration. These help a reviewer distinguish the implemented scope from future ideas.

## 04 · Keep the repository safe and reproducible

> 🎬 ЭКРАН. Раздел «Keep the repository safe and reproducible». Продолжай показ подготовленного примера. Выдели входные данные и решение именно этого раздела. Не прокручивай целый урок вместо демонстрации. Если это аналитическое упражнение, заполняй его рабочую таблицу по одному решению.

Before making a project public, inspect the files you are about to publish. Exclude authentication state, private keys, local configuration containing secrets and real customer data. Use synthetic records for demonstrations. The SAM starter already excludes common Salesforce authentication directories, but an ignore file cannot remove a secret that was previously committed. Use a separate development org and the repository instructions to rehearse setup. If you cannot test a step, label it unverified and explain the dependency. A screenshot of a successful interface is useful, but it does not prove that a clean checkout can reproduce the project. Capture the actual test output and the commit it belongs to, without including credentials.

## 05 · Guide the reviewer through one important decision

> 🎬 ЭКРАН. Раздел «Guide the reviewer through one important decision». Продолжай показ подготовленного примера. Выдели входные данные и решение именно этого раздела. Не прокручивай целый урок вместо демонстрации. Если это аналитическое упражнение, заполняй его рабочую таблицу по одному решению.

Prepare a two-minute walkthrough: the user problem, the visible feature, one key implementation decision and the verification. Open the relevant code instead of browsing through every folder. Show a failure case as well as a successful request. For example, an unavailable vehicle should produce a useful error rather than a misleading success message. Ask a peer to follow the README from a clean starting point. Record where they hesitate and improve those instructions. The aim is not to remove every question; good projects invite technical discussion. The aim is to make that discussion about your decisions and evidence rather than missing setup details.
