## 02 · Clarify the task before typing

> 🎬 ЭКРАН. Раздел «Clarify the task before typing». Продолжай показ подготовленного примера. Выдели входные данные и решение именно этого раздела. Не прокручивай целый урок вместо демонстрации. Если это аналитическое упражнение, заполняй его рабочую таблицу по одному решению.

Live coding combines implementation with communication. Begin by restating the requirement and asking about ambiguous inputs, expected output and constraints. For a practice task, use this request: “Given a list of test-drive records, return the number of requests for each vehicle.” Clarify whether records without a vehicle should be ignored and whether the method only reads the supplied records. For this lesson, ignore null vehicle references and do not query or update the database. The input list contains the data you need. This boundary makes the exercise small enough to discuss. If an interviewer adds database access or security requirements, treat that as a changed task and explain what additional decisions it creates.

## 03 · Sketch the algorithm and examples

Use a map from vehicle ID to count. For each record with a vehicle, read the current count or use zero, add one and store the result. Walk through three records: two for vehicle A and one for vehicle B. The result should contain A with two and B with one. An empty list should produce an empty map. Before coding, name the tests: empty input, repeated vehicle, multiple vehicles and a record without a vehicle. Decide how to handle a null list according to the agreed contract; you can reject it or return an empty result, but do not silently change the choice halfway through the exercise. These examples make your intended behaviour visible before syntax becomes a distraction.

## 04 · Review a flawed approach systematically

> 🎬 ЭКРАН. Раздел «Review a flawed approach systematically». Продолжай показ подготовленного примера. Выдели входные данные и решение именно этого раздела. Не прокручивай целый урок вместо демонстрации. Если это аналитическое упражнение, заполняй его рабочую таблицу по одному решению.

Imagine that a proposed solution queries all test drives for each vehicle inside a loop. It may return a correct count for a small example, yet it violates the stated input-only contract and repeats database work. A reviewer should first identify the mismatch in behaviour, then the scaling problem. “Queries in loops are bad” is less useful than explaining which unnecessary work occurs and how the input list already contains the needed information. Review in a consistent order: requirement, correctness, security where applicable, resource use, maintainability and tests. Do not spend the first five minutes discussing variable names while a method counts the wrong records. In a real code review, distinguish a blocking issue from an optional improvement and give a concrete example that demonstrates the concern.

## 05 · Narrate decisions and recover from mistakes

> 🎬 ЭКРАН. Раздел «Narrate decisions and recover from mistakes». Продолжай показ подготовленного примера. Выдели входные данные и решение именно этого раздела. Не прокручивай целый урок вместо демонстрации. Если это аналитическое упражнение, заполняй его рабочую таблицу по одному решению.

While coding, explain changes in your approach rather than every keystroke. “I am using a map so that each record updates one count” is helpful. If you make a syntax error, read the message, isolate the issue and correct it. Calm diagnosis is part of the work; pretending the error did not happen makes the reasoning harder to follow. Finish by running the agreed examples and reviewing the implementation against the contract. If time runs out, state what works, what remains and the next test you would run. Do not claim that unexecuted tests passed. For peer practice, alternate roles: one person implements the task and the other records clarifications, decisions and missed checks.
