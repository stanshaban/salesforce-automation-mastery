## 02 · Understand the mechanism

> 🎬 ЭКРАН. Раздел «Understand the mechanism». Продолжай показ подготовленного примера. Выдели входные данные и решение именно этого раздела. Не прокручивай целый урок вместо демонстрации. Если это аналитическое упражнение, заполняй его рабочую таблицу по одному решению.

Northstar wants an automatic follow-up when Irina's test drive is confirmed. A Flow can be a clear choice when the rule is straightforward, administrators maintain it, and existing automation remains understandable. A more complex allocation algorithm or a highly reused typed service may fit Apex better. Neither the number of clicks nor a developer's preferred tool is a sufficient decision rule. Start with the business operation, not the technology. State what triggers it, which records it reads and writes, the expected batch size, who maintains it, and what should happen when one record fails. Then locate the transaction boundary: must the follow-up succeed together with the confirmation, or may it be processed later? Moving work asynchronously changes the product's failure behavior, even if it reduces synchronous work.

Compare three requests. First, set a field on the same appointment when it changes to Confirmed. Second, create one follow-up record after confirmation, with a defined retry policy. Third, allocate vehicles across hundreds of appointments using a conflict-resolution algorithm. These differ in data access, failure handling, and complexity; they should not receive the same answer merely because all begin with a record change. For the hands-on part, use a simple same-record rule: when a Test Drive first becomes Confirmed, reject confirmation without Vehicle__c, Customer__c, or Scheduled_At__c. No new fields are required. A validation rule is worth considering before either Flow or Apex because the requirement is to prevent invalid data. Comparing three tools is useful when the third is the simplest expression of the requirement.
