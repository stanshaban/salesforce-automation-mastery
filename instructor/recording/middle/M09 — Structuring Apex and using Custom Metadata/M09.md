## 02 · Understand the mechanism

> 🎬 ЭКРАН. Раздел «Understand the mechanism». Продолжай показ подготовленного примера. Выдели входные данные и решение именно этого раздела. Не прокручивай целый урок вместо демонстрации. Если это аналитическое упражнение, заполняй его рабочую таблицу по одному решению.

A large warranty method often mixes several jobs: reading a vehicle, deciding whether to request a check, constructing HTTP, interpreting a response, saving status, and deciding retry timing. When one policy changes, this mixture makes unrelated behavior harder to understand. Separation is useful when each part has a distinct reason to change and a clear input/output contract. For Northstar, use three responsibilities. A policy object describes allowed attempts and timeout. A client adapter translates the warranty provider's request and response. An application service coordinates the vehicle, request state, and chosen client. This is a responsibility map, not a requirement to create an interface for every helper or a framework before the first use case works.

## 03 · Northstar Motors worked example

> 🎬 ЭКРАН. Раздел «Northstar Motors worked example». Продолжай показ подготовленного примера. Выдели входные данные и решение именно этого раздела. Не прокручивай целый урок вместо демонстрации. Если это аналитическое упражнение, заполняй его рабочую таблицу по одному решению.

Suppose the provider changes its JSON from covered to isCovered. That translation belongs in the adapter. If Oleg changes the allowed retry count from three to two, policy changes without rewriting HTTP parsing. If Northstar decides that a completed test drive must exist before requesting a warranty check, that eligibility rule belongs in the application behavior, not in the generic HTTP client. For the first implementation, avoid the network entirely. Create a small policy class with constructor arguments enabled, maxAttempts, and timeoutMillis. Have the orchestration accept the policy as input. The production entry point reads Custom Metadata and constructs the policy; unit tests construct explicit values. This keeps the local rule testable without pretending configuration and endpoint authentication were verified.
